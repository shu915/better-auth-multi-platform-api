今回の変更(git diff)を評価し、合格か要修正かを判定してください。
gofmt・go vet・go build・go test は Stop hook(`.claude/hooks/stop-checks.sh`)が毎回実行し、失敗していれば差し戻される。SKIP があれば hook が警告する。ここでは重複して実行しない。
評価は「改ざんの確認」と「コードレビュー」の2段階で行います。

## 進め方
1. `git diff` と `git status` で変更範囲を確認する(未追跡ファイルも含める)。
2. テストの改ざんを確認する(下の「改ざんの検出」)。
3. 今回変更されたファイルと、その呼び出し元・呼び出し先を読み、下の観点でレビューする。

## 改ざんの検出
検証が通っていても、通すためにテストや値を弱めていれば不合格にする。`git diff` の `_test.go` と設定値の差分を読み、次を探す。
- 削除されたテストやテストケース、新しく足された `t.Skip`、`-run` や build タグによる除外
- 期待値やアサーションが、仕様の変更ではなく実装の出力に合わせて書き換えられている(厳密な比較が `NotEmpty` 相当に緩む、期待するステータスコードが変わる、など)
- 上限値、タイムアウト、許可リスト、`MaxBioLength` のような検証用の値が、理由なく緩められている
- 実装を直さず、テスト側のモックや入力だけを変えて通している
見つけたら、他の指摘より先に「高」として挙げ、元の内容(差分の該当箇所)を引用する。仕様変更が理由なら、その根拠が差分や説明にあるかを確認し、なければ指摘する。

## レビュー観点
1. 【セキュリティ】:認可漏れ、インジェクション、機密情報の露出、レートリミット
2. 【パフォーマンス】:N+1問題、不要な再計算/再レンダリング、過剰なDB/API呼び出し
3. 【エッジケース・異常系】:null/undefined/空配列、外部連携のタイムアウトやエラー時の挙動
4. 【データ整合性・冪等性】:連打による二重処理の防止、トランザクションのロールバック漏れ
5. 【メンテナンス性】:命名の意図、関数の責務分割、型定義の厳密さ

プロジェクトの方針は `CLAUDE.md` に従う(標準の `net/http` のみ、ロジックは `internal/`、ハンドラは薄く、`UPDATE` では `updated_at = now()`)。

## 制約
- コードは書き換えない。指摘と修正例の提示だけを行う。
- ファイルの編集、コミット、マイグレーションの実行はしない。
- 推測で指摘せず、コードを読んで確認できたものだけを挙げる。

## 判定
- **合格(LGTM)**: 改ざんがなく、「高」「中」の指摘がない。
- **要修正**: テストの改ざん、または「高」「中」の指摘が1つでもある。
- SKIP されたテストは「通った」とみなさない。Stop hook の警告や `go test -v ./...` で何が SKIP されたか、なぜ(例: `TEST_DATABASE_URL` 未設定)かを確認して明記し、その部分は未検証と報告する(SKIP の確認だけは、必要なら `go test -v` を読み取り目的で実行してよい)。SKIP があっても、ほかが問題なければ合格にできるが、未検証であることを必ず書く。

## 出力形式
最初に判定を1行で書く:`判定: 合格` または `判定: 要修正`。

続けて、次の順に書く。
1. 改ざん確認の結果。gofmt・vet・build・test は hook が検証済みと一言添える
2. 指摘の一覧。指摘ごとに、重要度(高/中/低)、観点(1〜5)、場所(`ファイル:行`)、理由、修正コード例を書く。
3. 未検証の項目(SKIP など)

指摘が1つもなく、検証もすべて通り、未検証もない場合は「LGTM」とだけ答える。
